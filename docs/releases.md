# Release preparation

The source is published at [github.com/yukunlabs/lunlet](https://github.com/yukunlabs/lunlet) as a source preview and the product page at [yukunlabs.github.io/lunlet](https://yukunlabs.github.io/lunlet/); no signed download has been published yet. This workflow supports US-27 through US-30 and US-35; it does not establish MVP acceptance.

## Hosting and cost

The proposed zero-cost GitHub path is a public source repository, standard hosted runner, GitHub Releases for downloads, and a static GitHub Pages product page. [GitHub documents standard public runners as free](https://docs.github.com/en/actions/reference/runners/github-hosted-runners); [Pages is available for public repositories on GitHub Free](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages). Visibility remains the owner's decision. Private runner minutes/storage have a separate budget, so the prepared validation workflow skips private repositories.

[Validate](../.github/workflows/validate.yml) runs on pushes to main, pull requests and manual dispatch in a public repository; in a private repository only manual dispatch runs, so automatic events never consume the account's included macOS minutes. It has read-only repository permissions, pinned actions, a 15-minute timeout, no credentials or uploaded artifacts, and no publication step; the Swift build directory is restored from a cache keyed on the toolchain and the pinned dependencies, so a run rebuilds only what changed. It runs the module tests, traceability checks, release and site tests, and the static-site build. Review the account's current Actions quota and spending limit before relying on private manual runs. Native display/power tests and clean-machine acceptance stay local. The first hosted run used the `macos-26` runner with Apple Swift 6.3.3 on macOS 26.6. No larger runner, backend, domain, analytics or paid hosting is required.

GitHub does not supply Apple signing. A Gatekeeper-trusted macOS download requires a stable owner-controlled Developer ID Application identity, hardened runtime and notarization, which need a paid Apple Developer Program membership. By the owner's decision of 2026-11-01 the first downloadable release is instead an **unsigned preview**: a release-configuration build signed ad hoc, packaged with `LUNLET_RELEASE_UNSIGNED=1`, whose release notes and product page state that macOS asks to allow it on first open (System Settings › Privacy & Security › Open Anyway on macOS 15 and later; right-click › Open before that) (AC-27.05). Updates ask for nothing: since 2026-11-01 credentials live in Lunlet's user-only credential file rather than the Keychain, which would have asked for authorization after every update of an unsigned build. Sparkle still verifies each update with the EdDSA key. A signed, notarized release later replaces these notes. [Apple's distribution guidance](https://developer.apple.com/developer-id/) and [notarization requirements](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution) apply separately from GitHub Free. Membership, certificates and notarization credentials remain owner decisions; none are purchased, discovered or exported by these scripts.

## Prepare a candidate

1. Complete the confirmed acceptance criteria for the declared release scope and owner device tests. Resolve the [remaining integration gates](feasibility.md) and review the existing [0BSD license](../LICENSE), copyright identity, SPDX metadata and [provenance inventory](../NOTICE.md), including artwork rights and privacy claims. Source availability is not acceptance: Feishu, Telegram and Slack delivery and one reply per notice are verified live, as recorded there, while the remaining gates stay open.
2. After owner approval, set the version/build in `Resources/Info.plist`, commit the exact source, and create its matching `vMAJOR.MINOR.PATCH` tag. Tags and external publication are separate owner actions; contributions arrive through feature branches and pull requests.
3. On the release Mac, build from that clean tag using the stable `LUNLET_CODE_SIGN_IDENTITY`, or `LUNLET_CODE_SIGN_IDENTITY=- LUNLET_RELEASE_UNSIGNED=1` for an unsigned preview. `scripts/build-app.sh` embeds source revision/dirty state, copies available project/upstream notices before signing, and rejects dirty normal builds. `--preview` stays explicitly ad hoc and cannot become a release candidate. To let the candidate check for updates, also set `LUNLET_UPDATE_FEED_URL` and `LUNLET_UPDATE_PUBLIC_KEY` as described under [Updates](#updates-with-sparkle).
4. For a signed release, submit the candidate to Apple's notarization process using credentials configured by its owner and staple the successful ticket; an unsigned preview skips this step. The scripts do not read existing signing/notarization credentials, submit binaries or modify trust settings.
5. Run `LUNLET_RELEASE_TEAM_ID=<approved-team> scripts/package-release.sh /absolute/Lunlet.app v0.1.0` with the actual approved version, or `LUNLET_RELEASE_UNSIGNED=1 scripts/package-release.sh …` for an unsigned preview. Both require the exact source tag/revision, clean build marker, bundle identity/version and matching packaged licenses/notices; the signed path also requires the approved signing team, Developer ID signature, hardened runtime, stapled ticket and Gatekeeper assessment, while the unsigned path requires a valid ad hoc signature without the hardened runtime and records `ad hoc` signing and `none` for notarization in the manifest. It freezes the candidate before validation, retains the verified source revision, and rechecks source/notice consistency before exposing the result. It then creates, in a fresh ignored `.tmp/releases/<tag>.<candidate>` directory, an architecture-named disk image (the app beside an Applications link, the download people open), the matching ZIP (what the update feed serves), the manifest, notices and SHA256SUMS. It never signs, submits, uploads or overwrites a candidate.
6. Review that artifact on a clean Mac: download/unzip, move Lunlet to Applications, launch (for an unsigned preview, through the first-open steps the notes describe), configure the user's bot, quit/relaunch, install an update and verify that the saved bot connection is intact without any prompt. Record tested OS/architecture and known limits. The deployment target alone is not a tested support range.
7. Only after the owner authorizes publication, create a draft GitHub Release for the matching tag, attach the reviewed artifacts (the disk image first, then the ZIP, manifest, notices and checksums), and write concise release notes with requirements, checksums, capabilities, limitations and upgrade steps; an unsigned preview's notes open with the first-open steps. Review the draft before publishing, then publish the updated appcast as described below. No Homebrew integration is included.

These are prepared safeguards. The 0BSD license and copyright identity are selected; the provenance review for a binary release remains open. The binary release path is unverified until a matching source tag, a packaged candidate and a clean-machine update test exist. The local packaging check proves that development previews are rejected and that the unsigned mode accepts only an ad hoc signature; it does not prove cross-version credential continuity, which the clean-machine test records.

## Updates with Sparkle

Release builds use [Sparkle 2.10.1](https://github.com/sparkle-project/Sparkle/releases/tag/2.10.1) (US-35). `scripts/build-app.sh` embeds `Sparkle.framework`, signs its helpers, the framework and the app inside out with the same identity through `scripts/sign-app.sh`, and, for normal builds only, writes `SUFeedURL` and `SUPublicEDKey` from the environment. Only a certificate-signed build gets the hardened runtime and a secure timestamp: an ad hoc signature has no team identifier, and the runtime's library validation then refuses the app's own embedded framework at launch, so previews and the unsigned preview release sign without it. Both values or neither are required; the feed must use HTTPS, and `--preview` ignores them. A build without them, like every preview, never checks and shows no update controls. `Resources/Info.plist` keeps automatic checks on, automatic installation off and the system profile off. Sparkle's optional [signed feeds](https://sparkle-project.org/documentation/customization/) (`SURequireSignedFeed`) are not enabled: they would also authenticate the appcast and release notes, but make a lost key harder to recover from with ZIP releases, so they remain an owner decision. These are owner steps; the repository creates no key, feed, archive signature or release.

1. Use Sparkle's tools from the same version: download `Sparkle-2.10.1.tar.xz` from that release and use its `bin/` directory. After `swift package resolve`, the same tools are in `.build/artifacts/sparkle/Sparkle/bin/`.
2. Once, on the release Mac, run `bin/generate_keys`. It stores the EdDSA private key in the owner's login Keychain and prints the public key. Lunlet's public key is `EhftNv8sxDPjDmCQ+FELNAg9SlWVuHMTGpYU29qJwAg=`; every release build must carry exactly this key, or installed copies refuse its updates. The private key never enters this repository, CI, environment files or a release. If you export a backup with `generate_keys -x <file>`, keep that file offline. If it is lost, Sparkle accepts a new key only in an update signed with the same Developer ID certificate, as [Sparkle documents](https://sparkle-project.org/documentation/#rotating-signing-keys); an unsigned preview has no such fallback, so its users would reinstall by hand.
3. Build the candidate with `LUNLET_CODE_SIGN_IDENTITY`, `LUNLET_UPDATE_FEED_URL` (the final HTTPS address of `appcast.xml`) and `LUNLET_UPDATE_PUBLIC_KEY` (the printed public key), then notarize, staple and package it as above. Check that `manifest.json` names the intended `updateFeed`. The feed address is fixed in each released build; moving it requires a release that still reads the old feed.
4. Copy the packaged ZIP (not the disk image) into a new folder with its release notes under the same base name (the notes are `docs/release-notes/<tag>.md`, copied as `Lunlet-0.2.0-macos-arm64.md`), and run `bin/generate_appcast --download-url-prefix https://github.com/yukunlabs/lunlet/releases/download/v0.2.0/ <folder>`. It signs the archive with the Keychain key, reads the version and minimum macOS from the app, and writes an `appcast.xml` listing that release, which is all installed copies need. The prefix applies to every archive in the folder, so keep earlier releases out of it. Review the item's version, URL, length and `sparkle:edSignature`.
5. Publish the GitHub Release with that ZIP first, then the appcast at the exact feed address over HTTPS. The feed is the release asset `appcast.xml` reached through `https://github.com/yukunlabs/lunlet/releases/latest/download/appcast.xml` (owner decision of 2026-11-01), so every release attaches the current appcast and the latest published full release is the one installed copies read; a pre-release never becomes `latest`. Changing the appcast is what offers the update to installed copies.
6. Accept it on a clean Mac: install the previous signed release, publish the new one, confirm the footer notice appears without a window, open it, read the notes and install, and confirm that Lunlet relaunches with its settings, skins and saved bot authorization. Also confirm that turning automatic checks off stops background checks while Check for Updates… still works. Record the result in the feasibility notes; local checks with a synthetic feed do not count.

## Product page and optional support

`website/` contains a dependency-free single page. Every picture on it is a still of Lunlet's real interface with synthetic data: the opt-in [still render](../Tests/LunletDesktopTests/SiteAssetRenderTests.swift) draws them from the film's synthetic world (the display's top with the Overview open, each panel page, the cue island, the phone's notice on Feishu, Slack and Telegram before and after a reply, each read back from the message Lunlet composes for that channel, and the entry in each built-in skin), and `scripts/render-site-assets.sh` places them in `docs/assets/screenshots/`, which the README shares. The page uses the selected app icon, supports light/dark and reduced motion, and makes no account/network requests.

Three checks keep the page in step with the product, all run by Validate and before every publication. Each page section lists the stories it presents and the build refuses a story that is not confirmed, while a confirmed story that declares `Product page: #section` must be presented there. The page's facts (the agents, messengers and skins the app offers, its macOS target) are read from the Swift sources at build time, and the hand-written block for each agent, messenger or skin must exist for exactly the set the sources define. The stills and the film each carry a manifest of the sources they were rendered from; `scripts/check_site_assets.py` fails on stale stills (run `scripts/render-site-assets.sh`, which renders only when needed) and warns on a stale film (`scripts/render-film.sh`). Renders are not byte-stable across runs because the panel shows relative times, so a re-render rewrites every still; they are therefore rendered only when an input changed. Its copy distinguishes implemented read-only observation, verified notification delivery and one reply per notice from client workflows that still need on-device validation.

```sh
python3 scripts/build_site.py
python3 -m http.server 4173 --bind 127.0.0.1 --directory .tmp/site
```

The output directory must be new; a fresh output keeps unrelated local files out of deployment. Open `http://127.0.0.1:4173` locally. Static/configuration checks pass, and the page was reviewed in Chrome at a 1440-pixel desktop width and a 390-pixel phone viewport (layout, pictures, horizontal overflow); keyboard review remains outstanding. Stop the owned preview server after review.

Before publication, fill only owner-approved destinations in `website/config.json`: the actual repository, corresponding GitHub Release, and optionally the external support page. Configured source and release destinations must identify the same repository. Null destinations are omitted; the page never invents a download or payment link. "Buy me a coffee" remains a small secondary footer link, with payment methods/QR codes only on its destination. [The Pages workflow](../.github/workflows/pages.yml) publishes on every push to public `main`, on every published full GitHub Release and on manual dispatch, always from the pushed or released commit; it asks GitHub for the latest published full release and links its download only when one exists, so the page neither invents a download nor lags a merged change.

## Source-first launch

One repository holds the application source, the product page and the film, so the page and README share one product message: local Codex and Claude Code observation, recorded usage and allowance context, then locked-Mac completion notices on the selected channel. `website/` and the film composition are reviewable source; the Pages workflow builds and publishes only the static output. The page states that locked-Mac delivery and one reply per notice are verified on Feishu, Telegram and Slack, and shows no macOS download button until a signed release exists. A signed macOS package is a later milestone: it waits for Developer ID signing, notarization, clean-machine install/update checks and the remaining provider gates, and its GitHub Release and checksum stay tied to the exact source tag.

The film is a silent, captioned 16:9 product film with a poster frame and reduced-motion-friendly playback controls, rendered from Lunlet's own views so it shows the app's actual notch, panel and motion (AC-28.04) on a whole synthetic Mac display, and ending on a phone. It uses synthetic project names, sessions, prompts, people and account values; no actual account, conversation, credential or screen recording enters the asset. Its sequence: the whole display with a menu bar, an editor, a terminal running a coding agent and the lettering and vine at the notch; a push in to the notch for a task cue island; the panel opening on that conversation (AC-13.09), then closer for reading; the Codex limits' hover overview, the Overview, a day's detail and the Claude Code page; a follow-up prompt and its start cue; the Mac locking and its display sleeping; then a generic phone in front of the dark Mac showing the notification and the bot chat: the completion card with its reply box, the reply sent from the phone, and the card rewritten as delivered. The storyboard source and optimized MP4 live in the repository so a PR can review both; the site uses a click-to-play video with captions, no autoplay or analytics.

The current film is 59 seconds at 1920×1080, 30 fps, H.264 (yuv420p, BT.709, CRF 19) without audio, about 7.9 MB; its [captions](../website/video/lunlet-captions.vtt), MP4 and poster (the whole display with the panel open) are in `website/video/`. `scripts/render-film.sh` regenerates all three on a Mac with FFmpeg: the opt-in [film render](../Tests/LunletDesktopTests/ProductFilmRenderTests.swift) draws every frame offscreen from the real entry, cue islands, panel pages and hover overview, places them with Lunlet's own placement functions and surface springs, and approximates the window server's glass with the blurred, generated desktop. Its [scenery](../Tests/LunletDesktopTests/ProductFilmScenery.swift) draws the display and bezel, menu bar, windows, lock screen and phone in code with system fonts and no third-party logos; the phone's card text is read back from `SessionCard.render` for a synthetic locked-Mac completion, so it shows no reply control. Pass a new directory to keep the PNG frames; `LUNLET_FILM_TIMES=3,13.5` with `LUNLET_FILM_DIR` renders only chosen moments. Dates follow the render day. Frames were reviewed at half-second to one-second intervals; no browser or provider acceptance is inferred from the film.

Apply these GitHub settings at publication and check them in the repository settings afterwards; local YAML cannot establish hosted acceptance. Enable GitHub Pages with **GitHub Actions** as its build source, and `Publish product page` then runs on each push to `main` and each published release; the `github-pages` environment must allow deployments from the `main` branch and from `v*` tags, because a release run carries the tag as its ref (the first release's run was refused until that tag rule was added on 2026-11-01). Configure a `main` ruleset that requires the `validate` status check and resolved conversations and blocks direct pushes, force pushes and deletion; a second approving reviewer is required once another maintainer exists. Enable private vulnerability reporting so security reports follow [SECURITY.md](../SECURITY.md) rather than public Issues. Set `website/config.json` to the repository URL and leave the release URL null; the workflow derives the download link from the latest published full GitHub Release. An approved support destination is configured in `website/config.json` before the optional support link appears; payment identifiers, wallet addresses and collection QR codes never enter the repository or the page.

## Iterate after the first release

Work is organized by feature module: core, codex, claude, feishu, messaging, storage and desktop, the scopes of `scripts/test-core.sh`. Each change starts from an Issue or a confirmed story in [the requirements](requirements.md), lands through a short-lived feature branch and a pull request reviewed against [the pull request template](../.github/pull_request_template.md), and uses [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/) subjects; the [Validate](../.github/workflows/validate.yml) workflow must pass before merge. Versions follow [semantic versioning](https://semver.org/spec/v2.0.0.html) from 0.1.0, and the version in `Resources/Info.plist` matches the tag. Each release is tagged `vMAJOR.MINOR.PATCH` from `main`, repeats the packaging, signing, notarization and appcast steps above, and ships release notes listing requirements, checksums, capabilities, limitations and upgrade steps.
